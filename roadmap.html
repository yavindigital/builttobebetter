Development Roadmap

What to build.
In what order.

Five phases. Decisions to make before writing a line of code. Integrations to think through before you need them. Every phase earns the right to build the next.

Phase 1 — Sales Engine Phase 2 — Fulfillment Phase 3 — Automation Phase 4 — Monitoring Phase 5 — Agency
Before You Write Code

Decisions to make early.

These choices affect every phase. Getting them wrong costs more to fix later than getting them right now. Pick deliberately, not by default.

Database
Relational DB — PostgreSQL
You have 20+ related entities, complex audit queries, and need JSON columns for flexible image metadata. PostgreSQL handles all of it. Don't use SQLite in production.
PostgreSQL ✓ MySQL PlanetScale
ORM / Query Layer
Database Access
Prisma is the safest choice — excellent migration tooling, type-safe client, wide community. Drizzle is lighter and closer to raw SQL if you want more control. Pick one and commit to its migration workflow from day one.
Prisma ✓ Drizzle ✓ TypeORM Knex
Background Queue
Job Processing
Crawling and image analysis must never run inside a web request. BullMQ + Redis is the most capable option. pg-boss (Postgres-native) works if you want to avoid running Redis. Decide before you write the first crawl function.
BullMQ + Redis ✓ pg-boss ✓ Inngest Trigger.dev
Crawling Approach
HTTP vs. Headless Browser
HTTP + Cheerio is fast and cheap but misses JavaScript-rendered images. Puppeteer/Playwright sees everything but is slower and costs more at scale. Start with HTTP. Document the limitation. Add headless for a premium audit tier later.
Cheerio + Axios (MVP) ✓ Puppeteer Playwright Crawlee
Image Processing
Analysis & Conversion
Sharp handles WebP conversion, resizing, quality optimization, and can probe image dimensions without full decoding. Use it for both analysis and optimization. It's fast, it's a native binary, and it's the Node.js standard.
Sharp ✓ Jimp ImageMagick (CLI)
Authentication
User Auth & Sessions
For MVP, a simple email/password + JWT or session setup is fine. You control it, it's fast to build, and you don't pay per user. Clerk is excellent DX if you want to move faster on auth and would rather pay for it. Avoid rolling custom password hashing — use bcrypt.
Custom JWT/Session ✓ Clerk ✓ NextAuth / Auth.js Lucia
File Storage
Object Storage for Assets
Cloudflare R2 is S3-compatible with zero egress fees — excellent for serving optimized images. AWS S3 has the broadest ecosystem. Backblaze B2 is cheapest at scale. All three work. Pick R2 for the MVP unless you're already in AWS.
Cloudflare R2 ✓ AWS S3 Backblaze B2
Report Delivery
PDF Generation
The simplest approach: use Puppeteer to render your HTML audit report as a PDF. You already built the report in HTML — this gives you a perfect match. React PDF works too but requires rebuilding the layout in a PDF-specific API.
Puppeteer (HTML→PDF) ✓ React PDF pdfkit
Hosting
Deployment Platform
Railway and Render both support web + worker processes (critical for your queue workers) with easy PostgreSQL and Redis add-ons. Fly.io gives more control. Don't build on a platform that can't run persistent background workers.
Railway ✓ Render ✓ Fly.io AWS ECS

Phase 1 — Recommended
Phase 1

Sales Engine — the MVP.

Everything in Phase 1 exists to answer one question: "Is there a project worth selling here?" The MVP is done when a salesperson can walk out of the system with a report and a prospect.

Phase 1 — Launch
Sales Engine
Build enough to find a good prospect, prove the opportunity, generate a professional report, and begin tracking the sale. Human technicians handle fulfillment while the system learns.
Prerequisite: None — build this first
Domain Intake
  • Public submission form — URL, name, email, company, authorization acknowledgment
  • Internal intake — admin adds domain directly, no external form needed
  • URL normalization — strip trailing slashes, resolve www vs. non-www, enforce httpsTest edge cases early: query strings, subdomains, redirects
  • Duplicate detection — warn if domain already exists in system
  • Domain → Prospect association — link to account or prospect record
  • Authorization source recorded — who submitted, when, what they agreed to
Crawling Engine
  • Page discovery — follow internal links, find public pages
  • Sitemap detection — parse sitemap.xml if present
  • robots.txt compliance — respect Disallow directives
  • Configurable limits (stored in DB) — max pages discovered, max pages analyzed, crawl depth, concurrency, timeout, retriesNever hardcode these in application logic
  • Canonical deduplication — normalize URLs before storing
  • Pages discovered vs. analyzed stored separately — this distinction cannot be conflated
  • Crawl job states — QUEUED → RUNNING → COMPLETED / FAILED / RETRYING
Image Analysis Engine
  • Per-image collection — URL, source page, domain, MIME type, extension
  • File size measurement — HEAD request + Content-Length header
  • Dimensions — width and height via Sharp probe (no full decode required)
  • First-party vs. third-party classification — compare image hostname to crawled domainCritical — never count third-party as controllable opportunity
  • Existing WebP / AVIF detection — record current format, not just extension
  • Conversion eligibility flag — is this image a candidate?
  • Estimated savings calculation — bytes, percentage, projected full-site
  • Images discovered vs. images analyzed stored separately
Opportunity Scoring
  • Score 0–100 — composite of weighted inputs
  • Scoring inputs — image volume, legacy format %, payload, estimated reduction, oversized ratio, first-party control %, site scale, repeat image activity
  • Weights stored in DB — never hardcoded, configurable from admin
  • Tier classification — Healthy / Moderate / High / Very High
  • Tier thresholds configurable — stored in DB, not baked into code
Customer-Facing Audit Report
  • Executive summary — opportunity score + one-line verdict
  • Scan scope — pages discovered vs. analyzed (clearly labeled)
  • Image inventory — format breakdown, first vs. third-party
  • Payload analysis — current weight, estimated optimized, potential savings
  • Biggest opportunities — largest individual assets
  • Recommended next step — sales CTA at the bottom of every report
  • Methodology disclaimer — what is measured vs. estimatedEvery estimate must be labeled
  • Shareable URL — not email-only, linkable from any device
Admin Dashboard & Sales Pipeline
  • Domain list — audit status, score, sales state, assigned salesperson
  • Crawl job monitor — queue depth, running, failed — in the UI, not server logs
  • Failure surface — every failed job shows domain, error reason, retry option
  • Sales state machine — New Domain → Audit Complete → Qualified → Report Sent → Review Scheduled → Proposal Sent → Won / Lost
  • Prospect assignment — assign to salesperson
  • Audit history per domain — never overwrite, always append
  • Internal campaigns — group prospecting domains (e.g., "Texas Auto Dealers")
  • CSV export
Phase 1 Integrations
📧
Transactional Email
Resend · Postmark · SendGrid · AWS SES
Email is required in Phase 1 for audit report delivery. Set up a sending domain with DKIM and SPF before you send the first report. Use a subdomain like mail.builttobebetter.com.
  • Audit submitted confirmation — acknowledge receipt, set expectations on timing
  • Audit complete + report link — the primary delivery email
  • Internal alert — notify sales when a high/very-high score audit completes
  • Recommended: Resend (modern API, great DX, generous free tier) or Postmark (reputation for deliverability)
⚡
Background Queue
BullMQ + Redis · pg-boss
Required before the first crawl runs. Every crawl, image analysis, savings calculation, and report generation is a job with a status. If Redis feels like extra infrastructure, pg-boss runs entirely on your Postgres database.
  • DOMAIN_DISCOVERY — kick off crawl, find pages
  • PAGE_CRAWL — fetch and analyze a single page
  • IMAGE_FETCH — retrieve image metadata
  • IMAGE_ANALYSIS — calculate eligibility, size estimates
  • SAVINGS_CALCULATION — compute opportunity score
  • REPORT_GENERATION — build and store the report
⚠️JS-rendered images: A plain HTTP fetch won't see images injected by JavaScript. This is a real limitation for React, Vue, and many modern inventory systems. Accept it and document it in the audit methodology for MVP. Add a headless-browser option later as a premium scan tier.
⚠️Rate limiting: Crawl politely. Add configurable delays between requests. An automotive site can have 50,000+ pages — if you hammer it without limits, you'll get blocked, possibly flagged as an attack, and you'll damage the relationship with a prospect before they even know you exist.
⚠️URL normalization edge cases: www vs. non-www, http vs. https, trailing slashes, query parameters, fragment identifiers, and canonical redirects all create duplicate page problems. Test with at least ten real domains before you consider this reliable.
⚠️Large-site crawl limits are not optional: Configure them before the first production crawl. One large ecommerce site with no limits will consume your entire worker capacity and possibly the database. Make limits a first-class admin setting from day one.
Phase 2

Fulfillment System.

Build Phase 2 after Phase 1 audits are generating paying projects. The goal is to support the work operationally — not automate it. Human technicians still perform platform-specific replacements.

Phase 2 — Post-MVP
Fulfillment System
Support the optimization project from approval through delivery. Every original asset preserved. Every replacement traceable. A before/after proof report generated automatically at the end of every project.
Prerequisite: Phase 1 generating paid projects
Optimization Project Management
  • Create project from approved audit — link to audit, prospect, proposal
  • Project states — Created → Access Verified → Pre-Scan → Backup → Assets Collected → Optimized → Quality Review → Implementation → Site QA → Post-Scan → Results → Report → Closed
  • Three fulfillment modes — Direct (we replace), Assisted (we hand off files), Third-party limited (documented as out of scope)
  • Track implementer and approver — who did what, when
  • Project-level access control — technicians see only assigned projects
Pre-Optimization Baseline
  • Run a fresh scan before any changes — this is what "before" means
  • Baseline metrics stored — total payload, asset count, average size, largest image, legacy format count
  • Link baseline to project — not to the original sales audit, which may be weeks old
  • Baseline is immutable — never update it once stored; this is your reference point
Asset Collection & Management
  • Download first-party images — store originals before touching anything
  • File storage structure — organized by project, clearly separated originals vs. optimized
  • Generate optimized versions — WebP, quality-optimized, resized where oversized
  • Implementation map — which original URL maps to which replacement file
  • Per-asset approval — technician reviews quality before deployment
Replacement Tracking & Rollback
  • Every replacement logged — original URL, replacement URL, timestamp, project ID, performed by, approved by
  • Rollback record — the path back to the original for every single changed asset
  • Full project rollback — restore all originals if something goes badly wrong
  • QA checklist per project — confirm visual integrity before marking complete
Post-Optimization Proof
  • Post-scan after implementation — re-crawl and measure the live site
  • Comparison engine — before baseline vs. post-scan results
  • Calculated improvements — bytes removed, % reduction, assets converted, payload delta
  • Before/after report — customer-deliverable, not just internal data
  • Remaining issues flagged — what we didn't touch and why (third-party, out of scope)
Phase 2 Integrations
💳
Stripe — One-Time Payments
Project Invoicing
Phase 2 is when you first need to collect money in-system. Stripe Checkout or Payment Links are the fastest path — you don't need a full in-app billing UI to start. Set up the webhook endpoint now; you'll need it for subscriptions in Phase 4.
  • Create a Stripe customer when an account is created — store stripe_customer_id on the account
  • Project invoice → Stripe Checkout session or Payment Link
  • Webhook: payment_intent.succeeded → mark project as paid, release to production
  • Store stripe_payment_intent_id on every project
🗄️
File Storage
Cloudflare R2 · AWS S3 · Backblaze B2
Design the folder structure before the first file is stored. Changing it after projects are live is painful. Originals must never be in a public bucket. Optimized files can be served from a CDN-backed public bucket.
/accounts/{id}/projects/{id}/originals/
/accounts/{id}/projects/{id}/optimized/
/accounts/{id}/reports/{audit_id}.pdf
🔐
Credential Vault
Encrypted at rest · Role-scoped
Needed when technicians need WordPress logins, SFTP, or hosting API keys to perform replacements. Build the vault interface before you need it in Phase 3 automation — the data model must support it from here.
  • AES-256 encryption at rest — never plain text in the DB
  • Scoped to project or domain — not globally accessible
  • Role-restricted access — only assigned technicians can decrypt
  • Never logged, never in reports, never in error messages
  • Expiration and rotation support from the start
🔴Always store the original before any replacement. This is not optional. No production asset is modified without the original safely preserved in file storage first. The recovery path is a requirement, not a nice-to-have.
⚠️The first few projects don't need in-app Stripe billing. A Stripe Payment Link sent via email is fine. Get the project workflow working first, then build the in-app payment flow once you've run a few real projects through it.
⚠️Image quality review is not optional. WebP compression artifacts are real. Build in a human review step where a technician approves optimized files before they go into the implementation map. Don't ship to a customer's live site without this gate.
Phase 3

Automation.

Only build automation after completing 10–25 manual projects. Those projects will reveal which platforms appear most and what the real failure modes are. Automating assumptions is expensive.

Phase 3 — After Manual Projects
Platform Automation
Automate the most common replacement workflows based on what the first 10–25 real projects actually needed. Don't build integrations based on assumptions. Build them after paying projects reveal the patterns.
Prerequisite: 10–25 completed manual projects
Platform Detection
  • Detect CMS from crawl data — response headers, meta generator tags, HTML signatures, cookie names
  • Store platform classification — per domain, not per scan (update if it changes)
  • Platforms to detect — WordPress, WooCommerce, Shopify, Webflow, Squarespace, Wix, Drupal, custom
  • Confidence level — detected with certainty vs. likely vs. unknown
  • CDN detection — Cloudflare, Fastly, AWS CloudFront, KeyCDN — affects replacement approach
WordPress / WooCommerce
  • WordPress REST API — read/update media library entries
  • WP-CLI — direct CLI operations when server access is available
  • Media library replacement — update attachment file + metadata
  • Post content references — update img src in post bodies
  • Cache purging — Cloudflare, WP Super Cache, W3 Total Cache, LiteSpeed, Nginx FastCGIEach cache behaves differently — plan for all of them
  • WooCommerce product images — API-based replacement with size regeneration
Shopify & Other Platforms
  • Shopify Admin API — product image upload, replacement, deletion
  • Shopify theme assets — logo, banners, background images in theme files
  • Rate limit handling — Shopify API bucket rate limits require retry-with-backoff logic
  • Rollback via API — re-upload original if replacement causes issues
  • Other platforms — prioritize based on which appeared in real projects, not assumptions
🔴Do not build Phase 3 before Phase 1 is generating paying projects. The automation targets you think you need and the ones real projects actually need are different. Let 10–25 manual projects show you where automation pays.
⚠️WordPress caching is a major source of implementation failures. WP Super Cache, W3 Total Cache, Cloudflare, LiteSpeed Cache, and Nginx FastCGI all behave differently. An automated replacement that doesn't purge the right cache will look like it failed even when it succeeded. Test with each cache plugin explicitly.
⚠️Automated rollback is Phase 3 work. It depends on the replacement logging built in Phase 2. If the Phase 2 rollback records are clean and complete, automated rollback is straightforward. If they're not, it's dangerous.
Phase 4

Monitoring — recurring revenue.

After optimization, the customer's site keeps adding images. Phase 4 turns a one-time project into a subscription. This is the recurring revenue model.

Phase 4 — Recurring Revenue
Image Health Monitoring
Periodically rescan completed projects. Detect new images, format regressions, and payload drift. Report monthly or quarterly. The monitoring subscription is the product that makes Built to Be Better a platform, not a one-time service.
Prerequisite: Phase 2 completed projects
Scheduled Scan Engine
  • Cron-triggered monitoring scans — monthly or quarterly per account preference
  • Monitoring Scan entity — separate from Audit entity, linked to the project baseline
  • Never overwrite previous scans — each scan is a new record; history is the product
  • Scan scope mirrors original project scope — same pages, same limits
  • Job queue integration — MONITOR_SCAN job type, same states as crawl jobs
Comparison Engine
  • Current scan vs. last scan — detect additions, removals, changes
  • New images detected — how many, in what formats
  • New legacy-format images — JPG/PNG added since last scan
  • Previously optimized images reverted — CMS reset or CDN issue
  • New estimated payload waste — bytes, not just counts
  • Image health score — recalculated each scan, stored with trend history
Alerts & Reports
  • Alert triggers — new legacy images above threshold, payload spike, regression detected
  • Alert delivery — email + admin dashboard notification
  • Monthly/quarterly digest report — "264 new images — 231 healthy, 33 need attention"
  • Health trend visualization — image count, payload, score over time
  • Thresholds configurable per domain — stored in DB, not hardcoded
  • Recommendation engine — surface remediation options when issues found
Phase 4 — Stripe Subscriptions
💳
Stripe Billing — Recurring Subscriptions
Monthly monitoring · Quarterly monitoring · Managed optimization
What to build
  • Stripe Products + Prices for each monitoring plan (monthly, quarterly)
  • Stripe Customer per account — create at account setup, store stripe_customer_id
  • Stripe Checkout session for subscription signup
  • Stripe Customer Portal for self-service plan management and cancellation
  • Store per subscription: stripe_subscription_id, stripe_price_id, current_period_end, status
Webhooks to handle
  • invoice.paid — extend monitoring period, queue next scan
  • invoice.payment_failed — send dunning email, start grace period
  • customer.subscription.deleted — disable monitoring, retain historical data
  • customer.subscription.updated — handle plan changes and proration
  • All webhook handlers must be idempotent — Stripe may send the same event more than once

🔴Webhook handlers must be idempotent. Stripe delivers webhooks at-least-once, not exactly-once. If invoice.paid fires twice, your system should handle it gracefully without double-crediting the subscription.
⚠️Failed payment recovery needs a defined policy. What happens to monitoring scans during a grace period? Are they paused? Run but not delivered? Define this before you launch subscriptions — it affects customer trust significantly.
⚠️Monitoring scans and audits are related but distinct. A Monitoring Scan entity compares against a baseline. An Audit entity is a first-look analysis. Don't merge them in the data model — you'll regret it when generating trend data.
Phase 5

Agency & Enterprise.

Phase 5 turns Built to Be Better into infrastructure for agencies. One agency with 100 clients is more valuable than 100 individual clients. Build this after the underlying model is proven.

Phase 5 — Scale
Agency / Enterprise
Multi-account organizations, white-label reports, bulk domain import, partner pricing, and API access. This phase makes Built to Be Better a platform that agencies distribute to their own clients.
Prerequisite: Proven Phase 4 model, recurring revenue established
Multi-Account / Organizations
  • Organization entity — the agency account
  • Subaccounts — the agency's individual clients
  • Role: Agency — sees all subaccount domains, audits, projects
  • Role: Agency Technician — technical access limited to agency clients
  • Role: Read-Only Stakeholder — report access only
  • Agency dashboard — all clients in one view, scored and sorted
White-Label Reports
  • Agency branding on reports — logo, colors, name
  • Built to Be Better branding optional — configurable per agency
  • Custom sending domain — reports delivered from agency email
  • Branded report URL — optional custom domain support
Bulk Domain Import & Campaigns
  • CSV import — domains, vertical, assigned contact
  • Campaign grouping — "Texas Auto Dealers Q3"
  • Batch audit triggering — queue all imported domains at once
  • Bulk opportunity ranking — sorted results across all imported domains
  • Campaign-level reporting — aggregate scores, conversion stats
API Access
  • REST API — submit domains, retrieve audit results, get scores
  • API keys per organization — not user-level
  • Rate limiting — per key, configurable per plan
  • Webhook delivery — audit complete, score change, monitoring alert
  • OpenAPI / Swagger docs — machine-readable spec
  • Partner pricing tiers — configurable from admin, not hardcoded
⚠️Multi-tenancy data isolation is critical. Agency A must never be able to see Agency B's clients, audits, or reports. Build and test this at the data layer — not just the UI layer — before opening agency accounts.
⚠️API rate limiting must be built before the API is public. An agency with automation can submit thousands of domains at once. Rate limits protect your infrastructure and prevent one account from consuming all crawl capacity.

The Only Rule That Matters
Does this feature help us find a prospect,
prove the opportunity, sell the project, or complete it?

If yes — it belongs in the current phase. If no — it probably belongs in a later phase or not at all. Get the audit and sales engine generating paying projects before investing in automation. Let the first 10–25 paying projects teach you what fulfillment needs. The database you build by operating the business becomes the long-term competitive advantage.
