Development Principles

The rules that cannot be broken.

Accuracy Over Drama
Never make a report more impressive by overstating what was measured. A wrong confident number destroys trust faster than a qualified right one.
Measured vs. Estimated
Always distinguish them. Label every result. The platform's credibility depends on this. Every result must be classified as MEASURED, CALCULATED, ESTIMATED or PROJECTED.
Safety First
No production asset is replaced without a recovery path. Original file, URL, replacement, timestamp, project ID, who approved, who performed — all preserved.
Configurability
Thresholds, crawl limits, and scoring rules must not require code deployments to change. Pricing rules must not be buried in application code.
Observability
Operators must understand why a crawl failed. Surface failures clearly. Do not force developers to inspect server logs for routine business operations.
Historical Preservation
Never destroy previous scan data. Don't overwrite old audits with new ones. Trend history and baseline data become increasingly valuable over time.
Queue-Based Architecture
Crawling and image analysis never occur inside normal synchronous page requests. Every job has a status: QUEUED, RUNNING, COMPLETED, FAILED, RETRYING, CANCELLED.
Human Override
Staff must be able to correct classifications and decisions. Automation should augment human judgment, not eliminate the ability to override it.
Platform Independence
Do not create unnecessary customer dependence on Built to Be Better infrastructure. Optimized assets should remain usable by the customer independently.
Credential Security
WordPress, SFTP, API keys and hosting credentials are never stored as plain database text. Encrypted. Role-scoped. Audit logged. Never in application logs.
Discover vs. Analyze
Pages discovered and pages analyzed are fundamentally different things. The database must store them separately. Reports must never conflate them.
Image Claims vs. Speed Claims
Report "47% image payload reduction" when measured. Do not automatically claim "47% faster website." Speed is affected by JS, CSS, server, fonts, CDN and more.
Immediate Development Order

If uncertain about what to build next — use this.

Ask: "Does this feature help us find a good prospect, prove the opportunity, sell the project, or complete the project?" If yes — it belongs. If no — it probably doesn't.

  • 01Make crawling reliable.
  • 02Make measurement trustworthy.
  • 03Clearly separate discovered, measured, estimated and projected data.
  • 04Build opportunity scoring.
  • 05Build a report that a salesperson can actually sell from.
  • 06Build the internal admin and sales workflow.
  • 07Start running real domains through it.
  • 08Use actual projects to determine fulfillment automation requirements.
  • 09Build the before/after proof system.
  • 10Add recurring monitoring.
  • 11Add agency/enterprise capabilities after the model is proven.
Final Product Principle

Everything should reinforce one simple customer experience:

Find the Weight.
Measure the Opportunity.
Remove What Doesn't Need to Be There.
Prove the Difference.

Do not spend six months automating fulfillment before the audit and sales engine are producing paying projects. Get the intelligence layer trustworthy, run real sites through it, sell from the findings, and let the first 10–25 paying projects teach you what fulfillment actually needs to automate.
